## 1. How it works today

**GRAC CRM** (branded publicly as **GMOF / Generac Maintenance of Florida** at `genmaintoffl.com`) is a field-service CRM for a generator maintenance business. Staff run day-to-day ops in a web dashboard; customers see a thin invoice portal; the public site captures estimate leads and hosts pay links.

### Stack (verified)

| Layer | Tech | Location |
|--------|------|----------|
| Web UI | Next.js 16 App Router, React 19, Tailwind 4, Zustand | `client/` |
| API | Express + TypeScript, Zod schemas, Helmet/CORS | `server/` |
| Primary DB | MongoDB / Mongoose | `server/src/models/mongo/` |
| Legacy DB | MySQL via `mysql2` — **not connected at API boot**; used by one-off scripts | `server/src/config/mysql.ts` |
| Mobile | SwiftUI companion (~2.3k LOC) | `ios/GMOF/` |
| Deploy | Render Blueprint | `render.yaml` |

**README caveat:** `README.md` still describes auth as stubs and MySQL as the home for users/permissions. That is outdated. Auth is fully implemented in `server/src/routes/auth.routes.ts`; users, roles, and permissions live in MongoDB.

### Who uses it

| Role | Typical use |
|------|-------------|
| **super-admin** | Everything + Roles & Permissions + Admin Panel (payment platform apps, Cloudinary, public assets) |
| **admin / owner** | Full ops: leads, customers, contracts, schedule, messaging, Control Panel, users, territory |
| **manager / tech** | CRM + jobs/schedule (techs also write contracts); no Control Panel / messaging by default |
| **agent** | Leads + customers/contacts/contracts (read-heavy); **no Schedule** in nav |
| **customer** | Own invoices (and settings/notifications pages); legal consent gate |

Permissions are fine-grained strings (`leads:read`, `jobs:write`, `messages:*`, `integrations:*`, etc.) seeded in `server/src/models/mongo/RolePermission.ts`. JWT auth reloads permissions from the DB on each request so grants apply without re-login (`server/src/middleware/auth.middleware.ts`).

### End-to-end flows

**Lead → customer → job → invoice**

1. Prospect fills `/estimate` (3-step wizard) → unauthenticated `POST /leads` (`createLead`).
2. Staff manage status (`new` → `contacted` → `qualified` → `won` / `lost`) on `/dashboard/leads`.
3. **Convert** (`POST /leads/:id/convert`): dedupe by address/ZIP or phone/email; either link an existing customer or create a **temporary** customer + primary site (`CustomerAddress`) + contact (`CustomerContact`). Lead gets `customerRef` / `convertedAt` (status is not auto-flipped to `won`).
4. Staff **promote** the customer when ready (`isTemporary` cleared), then attach **contracts** from templates and/or **work orders** (jobs).
5. Work orders carry assignee + `scheduledStart`/`scheduledEnd`; dispatchers use `/dashboard/schedule` with queue, staff availability, drive-time suggestions (`/schedule/suggest`), and routes.
6. **Invoices** are created from contract initial/renewal or work-order sources. Staff mint a **pay link** (`POST /invoices/:id/pay-link`); customer opens `/pay/?token=…` and checks out via Square, Stripe, or PayPal. Webhooks mark invoices paid; renewal payments can advance contract renewal history.

**Staff schedule / dispatch**

- Schedulable users have `schedulable`, home location, weekly hours, and exceptions on `User`.
- Territory (counties/ZIPs on owners) drives `customer.ownerUserRef` for ownership/payment routing — separate from day-of tech assignment on the work order.
- Dispatcher roles: `super-admin` | `admin` | `owner` (UI helper in `client/src/lib/schedule.ts`).

**Payments & renewals**

- Per-seller credentials live in Control Panel (`PaymentProviderAccount`); platform OAuth apps (Square today) in Admin Panel (`PaymentPlatformApp`).
- Secrets at rest use AES-256-GCM (`server/src/utils/credentialsCrypto.ts`).
- Daily cron (06:00) opens renewal invoices within `RENEWAL_INVOICE_LEAD_DAYS` (default 30); Square OAuth tokens refresh every 12h (`server/src/jobs/scheduler.ts`).

**Public estimate & marketing assets**

- Landing `/` + estimate funnel feed the lead pipeline.
- Public assets: staff upload via Cloudinary creds → slug URLs (`GET /public-assets/:slug`) rewritten on the static host in `render.yaml`.

**Messaging**

- Admin/owner SMS hub: Twilio accounts, templates, threads, inbound/status webhooks under `/webhooks/twilio`.

**iOS**

- Login + read-mostly dashboards for staff (customers, contracts, leads, invoices, notifications) and customers (invoices). No schedule, messaging, Control Panel, estimate, or pay-link flows.

## 2. Architecture snapshot

### Key folders

```
client/src/app/          # App Router pages (static export → out/)
client/src/components/   # Feature UI (estimate, schedule, messaging, control-panel…)
client/src/lib/          # api.ts, dashboard-nav, role helpers
client/src/store/        # Zustand auth / notifications / consent

server/src/routes/       # Thin routers + permission gates
server/src/controllers/  # Request handlers
server/src/models/mongo/ # Mongoose models
server/src/services/     # Payments, Twilio, email, schedule, notifications
server/src/payments/     # Square / Stripe / PayPal adapters
server/src/jobs/         # Cron: renewals + Square OAuth refresh
server/src/migrations/   # Deploy-time idempotent migration ledger
server/src/scripts/      # One-off backfills, seed-admin, copy-prod-to-dev…

ios/GMOF/                # SwiftUI + APIClient (GET-focused)
```

### Request path

```
Browser / iOS
  → NEXT_PUBLIC_API_URL (or hardcoded Render URL on iOS release)
  → Express (helmet, CORS from CLIENT_URL, JSON body)
  → route → authenticate / requirePermission|requireRole
  → controller → Mongoose models / payment|Twilio|email services
  → MongoDB
```

Webhooks bypass normal JSON/CORS assumptions: Twilio URL-encoded under `/webhooks/twilio`; payment providers get raw body under `/webhooks/payments` for signature verification (`server/src/app.ts`).

Client is a **static export** (`output: 'export'` in `client/next.config.ts`) — all data loads client-side from the API; detail pages use query params (e.g. `/dashboard/customers/detail?id=…`) so the static host does not need dynamic segments.

### Notable integrations

| Integration | Where configured | Purpose |
|-------------|------------------|---------|
| Square / Stripe / PayPal | Control Panel + Admin platform apps; adapters in `server/src/payments/` | Checkout, pay links, webhooks |
| Square OAuth | Admin / env `SQUARE_*`; `squareOAuth.service.ts` | Connect merchant accounts |
| Cloudinary | Admin Panel credentials | Public marketing assets |
| Google Maps / Routes / Address | Control Panel Google credentials | Geocode, schedule drive-time, address validation |
| Twilio | Control Panel | SMS / call communications |
| SMTP / email accounts | Control Panel (+ env SMTP fallback) | Password reset, transactional mail |
| Census geocoder | `utils/censusGeocoder.ts` | Fallback geocoding |

### Deploy / config

- `render.yaml`: Node web service (`grac-crm-server`) + static site (`grac-crm-client`); `preDeployCommand: npm run migrate` (paid Render only — free plan needs `deploy.sh` / manual migrate).
- Env: Mongo URI, `JWT_SECRET`, `CREDENTIALS_ENCRYPTION_KEY`, `CLIENT_URL`, `PUBLIC_API_URL`, optional Square/SMTP/MySQL. Dev defaults exist in `server/src/config/env.ts` so local boot works without `.env`.
- Branding site URL baked as `NEXT_PUBLIC_SITE_URL=https://genmaintoffl.com`.

### Testing / lint / CI

- **No automated test suite** found (no Jest/Vitest/Playwright specs in-repo).
- **No GitHub Actions workflows** under `.github/`.
- Lint: `npm run lint` in `server/` and `client/` (ESLint). Server has known pre-existing lint noise; client is expected clean per `AGENTS.md`.
- Migrations: small ledger in `server/src/migrations/manifest.ts` (contacts, provision users, contracts collection/dates). Many operational scripts remain manual under `server/src/scripts/`.

## 3. Strengths

1. **Real domain coverage for a service business** — leads, multi-site customers, equipment, contracts with renewal standing, work orders, dispatch suggestions, invoices, and multi-provider payments are wired end-to-end, not just mocked.
2. **Permission model is thoughtful** — role + permission strings, DB-backed grants refreshed per request, system roles seeded on boot (`Role` / `RolePermission`).
3. **Payments architecture is modular** — provider adapters + registry, hashed/expiring pay tokens (`mintPayToken` uses 24 random bytes, SHA-256 hashed at rest), webhook signature path with raw body.
4. **Ops credentials are encrypted at rest** (AES-GCM) and largely managed in-product (Control Panel / Admin) rather than only via env.
5. **Deploy story is documented** — Render blueprint, migration runner with ledger, `deploy.sh` guardrails for production.
6. **Public funnel exists** — marketing landing, estimate wizard, tokenized pay page, legal pages, customer legal-consent gate.
7. **Territory + schedule** reflect real FL field ops (counties/ZIPs, drive-time via Google Routes).
8. **iOS companion** already authenticates against the same API and covers the highest-value read surfaces for staff and customers.

## 4. Improvements (ranked)

Items are ordered by recommended attention (security/ops first, then product leverage, then debt/DX).

### 1. Fail closed on production secrets

| | |
|--|--|
| **Problem** | `JWT_SECRET` and `CREDENTIALS_ENCRYPTION_KEY` fall back to hardcoded dev defaults if unset (`server/src/config/env.ts`). A misconfigured Render deploy would mint forgeable JWTs and decrypt/encrypt integration secrets with a public key. |
| **Evidence** | `env.ts` lines ~49–57: `"dev-secret-change-in-production"` and a fixed 64-char hex default. |
| **Fix direction** | On `NODE_ENV=production`, refuse to boot unless both are set and non-default; add a deploy checklist / health warning. |
| **Effort** | S |
| **Impact** | **High** — **critical security/ops** |

### 2. Rate-limit and abuse-harden public intake

| | |
|--|--|
| **Problem** | `POST /leads` is public with Zod validation only — no rate limit, CAPTCHA, or IP throttle. Easy spam/PII flood of the pipeline and notification stream. |
| **Evidence** | `server/src/routes/lead.routes.ts` (`router.post("/", createLead)`); no `rateLimit` usage anywhere under `server/src`. |
| **Fix direction** | Edge/API rate limits + honeypot/CAPTCHA on `/estimate`; optional source/API-key for trusted partners. |
| **Effort** | S–M |
| **Impact** | High |

### 3. Document and rotate the seed-admin credential story

| | |
|--|--|
| **Problem** | `seed-admin.ts` creates a well-known email/password pair. Fine for local bootstrap; dangerous if ever run (or left unchanged) against production. |
| **Evidence** | `server/src/scripts/seed-admin.ts`; also called out in `AGENTS.md`. |
| **Fix direction** | Require interactive password / env override; refuse when `NODE_ENV=production` unless an explicit force flag; rotate any shared prod password; prefer invite-only first admin. |
| **Effort** | S |
| **Impact** | High (ops hygiene) |

### 4. Close the lead→customer→sold loop in product UX

| | |
|--|--|
| **Problem** | Convert creates temporary customers but does not set lead status to `won`, and promotion / first contract / first invoice are separate manual steps. Staff can leave leads “converted” but still `qualified`, and temporary accounts uncleared. |
| **Evidence** | `convertLead` in `lead.controller.ts` sets `customerRef` / `isTemporary: true` without status=`won`; promote is a separate customer endpoint. |
| **Fix direction** | Guided “Convert & book” wizard: status transitions, promote, optional contract template + initial invoice in one flow; dashboards for temporary customers aging. |
| **Effort** | M |
| **Impact** | High (revenue ops) |

### 5. Customer portal depth

| | |
|--|--|
| **Problem** | Customers mainly see invoices in nav; notifications/settings exist but are secondary. No self-serve contracts, upcoming service, or easy re-pay from history beyond staff-issued links. |
| **Evidence** | `client/src/lib/dashboard-nav.ts` — customer sees Invoices only; iOS customer tabs mirror that thinness. |
| **Fix direction** | Customer home: open invoices, next service date, contract standing, pay CTA, message/contact. |
| **Effort** | M |
| **Impact** | Med–High |

### 6. Scheduling maturity for techs / agents

| | |
|--|--|
| **Problem** | Agents are excluded from Schedule despite lead/CRM access; tech mobile (iOS) cannot see or update jobs in the field. |
| **Evidence** | `dashboard-nav.ts` `excludeRoles: ["customer", "agent"]` on Schedule; iOS has no schedule/work-order API usage. |
| **Fix direction** | Role-appropriate schedule views; iOS “My jobs today” with status updates. |
| **Effort** | L (web + iOS) |
| **Impact** | High for field ops |

### 7. Messaging permissions for managers (not only admin/owner)

| | |
|--|--|
| **Problem** | SMS hub is gated to admin/owner/super-admin in nav and default `messages:*` seeds — managers who own day-to-day customer comms may be locked out. |
| **Evidence** | `RolePermission` `MESSAGES_PERMISSIONS`; nav `includeRoles` on Messaging. |
| **Fix direction** | Product decision: grant `messages:read/write` to manager (and maybe tech send-only); expose in Roles UI. |
| **Effort** | S |
| **Impact** | Med |

### 8. Payment OAuth parity (Stripe / PayPal)

| | |
|--|--|
| **Problem** | Square Connect OAuth exists; Stripe/PayPal seller OAuth UI is explicitly “coming soon” — more manual credential paste friction and error risk. |
| **Evidence** | `PaymentProvidersCard.tsx` “coming soon” buttons. |
| **Fix direction** | Finish OAuth for Stripe Connect / PayPal partner where needed, or clearly document manual-only forever. |
| **Effort** | M–L |
| **Impact** | Med |

### 9. Automated tests on money and auth paths

| | |
|--|--|
| **Problem** | No CI and no automated tests around pay tokens, webhook signature verification, convert/dedupe, or permission gates — regressions will be caught in production. |
| **Evidence** | No test files / `.github/workflows`; only lint scripts in package.json. |
| **Fix direction** | Start with API integration tests: authz matrix, `mintPayToken` checkout, payment webhook happy/fail, lead convert dedupe. Add a GitHub Action for lint + those tests on PR. |
| **Effort** | M |
| **Impact** | High (reliability) |

### 10. README / ops docs drift

| | |
|--|--|
| **Problem** | README still says auth stubs and MySQL-primary users — onboards people incorrectly and conflicts with `AGENTS.md`. |
| **Evidence** | `README.md` “Auth stub” table vs live `auth.routes.ts`; MySQL “users/accounts/permissions” claim vs Mongo models. |
| **Fix direction** | Rewrite README to match Mongo-primary reality, estimate/pay public routes, Control Panel config, seed-admin, Render free-plan migrate note. |
| **Effort** | S |
| **Impact** | Med (DX) |

### 11. iOS legal consent & write paths

| | |
|--|--|
| **Problem** | Web forces customer legal consent; iOS decodes the fields but does not gate. Customer detail is stubbed (“coming soon”). |
| **Evidence** | `ios/GMOF/CustomersView.swift` empty state; web `AuthGuard` / `legal-consent` pages. |
| **Fix direction** | Parity gate for legal docs; then prioritize job list / invoice pay deep-link over full CRM edit. |
| **Effort** | M |
| **Impact** | Med (compliance + mobile usefulness) |

### 12. Static-export / SPA tradeoffs

| | |
|--|--|
| **Problem** | Static export simplifies Render hosting but means no SSR/SEO for marketing beyond what’s in the static HTML, no Next middleware auth, and query-param detail URLs. Fine for now; may constrain marketing SEO and deep-link cleanliness later. |
| **Evidence** | `client/next.config.ts` `output: "export"`; `render.yaml` static site + rewrite for public assets. |
| **Fix direction** | Keep for ops app; consider a small SSR/marketing surface or prerendered estimate landing if SEO becomes a priority. |
| **Effort** | L if migrating off static export |
| **Impact** | Low–Med |
